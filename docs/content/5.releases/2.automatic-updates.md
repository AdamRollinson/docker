## PHP releases

A scheduled workflow, `.github/workflows/php-version-bump.yml`, runs every four hours and executes `alpine/check-php-versions.sh --update`.

The images compile PHP from php.net's own tarballs, so the script asks php.net directly. For each minor it reads the releases feed (`releases/index.php?json&version=<minor>`), or for a minor with no final release yet the pre-release feed (`pre-release-builds.php?format=json`), which also gives the release manager's download path. When php.net has a newer release it rewrites the whole line in `php-versions.txt` with the release, the SHA256 of the `.tar.xz` and its URL, so the build compiles exactly what was checked. The workflow then commits the change to `main` and dispatches the build workflow, which publishes the new exact tag and moves the minor tag.

```text
PHP 8.2: pinned 8.2.34, php.net 8.2.35 (security release), update available
PHP 8.3: pinned 8.3.36, php.net 8.3.36
PHP 8.4: pinned 8.4.27, php.net 8.4.27
PHP 8.5: pinned 8.5.12, php.net 8.5.12
PHP 8.6: pinned 8.6.0_rc4, php.net 8.6.0_rc4 [pre-release channel, tag 8.6-rc]
PECL igbinary (*): pinned 3.2.17RC1, latest stable 3.2.17RC1
PECL redis (*): pinned 6.3.0, latest stable 6.3.0
1 PHP update(s) available, run with --update to apply
```

The "security release" wording comes from php.net's own release tags.

### PECL extensions

The same run compares each line of `alpine/php/pecl-extensions.txt` with PECL's latest stable release. A newer release in the same major.minor (a patch release) is applied by `--update`, with a fresh checksum, and committed with the PHP pins. A new major or minor is only reported, because it can drop support for an older PHP, so it is a manual change. Lines that point at an `https://` URL (the Xdebug alpha for 8.6) are skipped.

### Pre-releases

The pins keep Alpine's spelling for release candidates (`8.6.0_rc4`), so the image tags stay the same, while php.net and PHP itself say `8.6.0RC4`. The script converts php.net's spelling, the build converts the pin back to find the tarball and normalises both before asserting the installed version, and the check treats a final release as newer than any pre-release of the same base, so the pin moves to 8.6.0 automatically when it lands.

A pre-release pin is published on a channel tag (`8.6-rc`) rather than the bare minor, which the check reports as `[pre-release channel, tag 8.6-rc]`. The build that pins the final release is the first to publish `php:8.6`; the channel tag stays where it was.

### Running it yourself

```bash
alpine/check-php-versions.sh             # report only
alpine/check-php-versions.sh --update    # rewrite php-versions.txt and PECL patch releases
```

The workflow can also be started from the Actions tab with "Run workflow".

Each bump is recorded on the [changelog](/releases/changelog), announced through the webhook when `NOTIFY_WEBHOOK_URL` is set, and once the build publishes it a GitHub release `php-<release>` is created with the image digests (see [Release pipeline](/releases/release-pipeline#release-notes)).

## Alpine base and GitHub Actions

Dependabot checks three ecosystems weekly:

- `docker` for `alpine/base` and `alpine/php` (the php-slim stage pins the same digest), so the digest-pinned `alpine:3.24@sha256:...` lines move together when Alpine publishes a new image.
- `github-actions`, so every pinned action SHA moves when a new release is tagged.
- `npm` for the documentation site in `docs/`.

Minor and patch updates are grouped, so each ecosystem produces at most one weekly pull request against `develop` for them. Every major update arrives as a pull request of its own, so a breaking upgrade can be reviewed, fixed or closed without holding back the rest. TypeScript major updates are skipped for now, because typescript-eslint does not support TypeScript 7 yet. The image build only runs on pushes to `main`, so the bumps are built, scanned and smoke tested when `develop` is merged into `main`; the docs CI runs on the grouped pull request itself whenever it touches `docs/`. Security updates are the exception: Dependabot always opens those against `main`, one per advisory.

## System packages

The weekly rebuild described on [Release pipeline](/releases/release-pipeline) republishes every tag with `apk upgrade` applied, so Alpine security fixes that do not involve PHP still ship within a week, and immediately if anything else triggers a build.
