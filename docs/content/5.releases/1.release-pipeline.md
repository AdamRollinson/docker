Builds run in GitHub Actions from `.github/workflows/docker-build.yml`. They are triggered by a push to `main`, a manual dispatch, and a weekly schedule.

## Jobs

```
php-matrix ─────────────────────────────┐
                                        ├──▶ build-php (minor × arch) ──▶ publish-php (per minor)
build-base (amd64, arm64) ──▶ publish-base ┘      php ──▶ php-nginx ──▶ php-nginx-dev
                                                    php ──▶ php-fpm
                                                    php ──▶ php-dev
                                                    php ──▶ php-slim (slim target)
```

1. **php-matrix** reads `alpine/php-versions.txt` and produces two matrices: one entry per minor for the publish jobs, and one per minor and architecture for the build jobs. Each entry carries the moving tag to promote to: the bare minor for a final release, or a channel tag such as `8.6-rc` for a pre-release pin.
2. **build-base** runs once per architecture, **publish-base** joins the two results into `rollogi/base:latest`.
3. **build-php** runs once per minor and architecture on a native runner and chains `php`, then `php-slim` (the `slim` target of the same Dockerfile, reusing the cached build stage), then `php-nginx` from the `php` digest it just pushed, then `php-nginx-dev` from the `php-nginx` digest, and `php-fpm` and `php-dev` from the `php` digest. Every image is scanned and smoke tested on that architecture before its digest is handed on.
4. **publish-php** runs once per minor, joins the amd64 and arm64 digests of each image into a manifest list under the candidate tag, attaches the VEX statement, promotes, signs and cleans up.
5. **release** creates a GitHub release for every PHP release that reached its exact tag for the first time, and **notify** posts the outcome to a webhook if one is configured.

## Native multi-architecture builds

Each architecture is built on its own runner, `ubuntu-24.04` for amd64 and `ubuntu-24.04-arm` for arm64, with buildx and the `docker-container` driver. No QEMU is involved, so the arm64 half builds at full speed and, more importantly, the smoke tests run natively on arm64 as well as amd64: an extension that only fails to load on one architecture is caught before it is published.

A build job pushes its single-platform image by digest (`push-by-digest`), never by tag, and passes the digest to the publish job as a workflow artifact. The publish job creates the manifest list with `docker buildx imagetools create` from the two digests. Layers are cached in the GitHub Actions cache, one scope per image and architecture.

A minor never waits for another: the publish job runs whenever the workflow was not cancelled, and a minor whose build failed simply has no digests to publish and fails on its own while the others go out.

## Candidate, scan, promote

Each single-platform image is first built straight into the runner's own Docker daemon. On the runner that built it, Trivy scans that local copy for CRITICAL and HIGH findings with fixes available, then `alpine/test.sh` runs the smoke tests against it, so nothing is pulled back from Docker Hub and nothing is pushed before it passes: health endpoint, exact PHP version, required extensions, every PHP package at the same release, no setuid binaries, tagged logs, the read-only rootfs recipe, root and arbitrary-user modes, the pinned HTTPS redirect host, the metrics listener, cron, mail relay, worker mode, `APP_INSTALL` and the Xdebug toggle on the dev image. A failure in either step stops the job before anything is pushed. Only then is the same build repeated from the layer cache with SBOM and provenance attestations and pushed by digest.

The publish job joins the two digests into a manifest list under `candidate-<git sha>` (base) or `candidate-<git sha>-<minor>` (PHP images), attaches the VEX attestation, then `docker buildx imagetools create` retags the candidate as the real tags, copying the whole manifest list including the SBOM, provenance and VEX. Finally the candidate tag is deleted through the Docker Hub API.

::note
The Docker Hub token used by CI needs the Delete scope for that last step. Without it, candidate tags are left behind but nothing else is affected.
::

## Release notes

Every published PHP release gets a [GitHub release](https://github.com/AdamRollinson/docker/releases) tagged `php-<release>`, for example `php-8.4.27`, created by the build that promotes that exact tag. Only minors promoted by the same run are considered, so a tag that already sits on Docker Hub from an earlier run is never released again by a later build. The notes list the manifest digest of `php`, `php-nginx` and `php-nginx-dev` for that release, which tags moved, and the `cosign verify` command. Pre-release pins are marked as pre-releases. The notes come from `alpine/release-notes.sh`, which you can run locally against Docker Hub for any published release. The [changelog](/releases/changelog) page on this site is the short form, one line per pin change.

## Notifications

Set a `NOTIFY_WEBHOOK_URL` repository secret and the pipeline posts a JSON message at three points: when the four-hourly check bumps a pin, when a build publishes, and when a build fails. The payload carries the message under both `text` and `content`, so Slack and Mattermost incoming webhooks and Discord webhooks work without a connector, and it includes `status`, `title`, `message`, `run_url`, `repository` and `sha` fields for anything that parses JSON itself. Without the secret the steps are a no-op.

## What is pinned

- **Actions** are pinned to commit SHAs and kept current by Dependabot.
- **buildx** is pinned to a release via `BUILDX_VERSION`.
- **The Alpine base** is pinned to a digest and kept current by Dependabot.
- **PHP** is pinned per minor in `php-versions.txt` (release, tarball SHA256 and URL) and kept current by the bump job. The tarball's signature is checked against the php.net release managers' keyring in `alpine/php/php-keyring.asc`.
- **PECL extensions** are pinned with checksums in `alpine/php/pecl-extensions.txt`; the bump job applies patch releases.

## Weekly rebuild

The schedule rebuilds everything every Monday even when nothing in the repository changed. Because the base Dockerfile runs `apk upgrade`, this is how Alpine's fixes for musl, OpenSSL, Nginx and other system packages reach the published images without a code change.

The layer cache would otherwise defeat this: an unchanged Dockerfile reuses the cached `apk` layer and its old packages. The `php-matrix` job therefore runs `alpine/apk-index-hash.sh`, which hashes every package name and version in the base image's Alpine release branch (main and community, the only repositories any image installs from) on both architectures, and every build receives it as the `APK_INDEX_HASH` build argument, declared just before each `apk` step. The cached layer is reused only while Alpine has published nothing new, and is rebuilt as soon as it has.

## Secrets and permissions

The workflow needs a `DOCKER_USER` variable (the Docker Hub account that logs in; it must be a member of the `rollogi` organisation with write access to the four repositories) and a `DOCKER_PAT` secret for that account, plus the optional `NOTIFY_WEBHOOK_URL` secret. The token is passed only to the login step and the candidate cleanup step, never exposed at workflow scope. The workflow runs with read-only repository permissions except for the release job, which needs `contents: write` to create tags and releases.
