## Non-root by default

Every image runs as `appuser`, UID 1000 and GID 1000, unless you pass `--user`. In this mode:

- Ports below 1024 cannot be bound. Use `NGINX_PORT=8080` and `NGINX_SSL_PORT=8443`.
- Cron works: it runs through supercronic as the same unprivileged user. See below.
- PHP-FPM runs its workers as `appuser` too; the `user` and `group` pool directives are stripped automatically.
- Nothing in `/etc` is writable. Configuration is rendered into `/run/nginx` and `/run/php`.

## Root mode

```bash
docker run --rm -d -p 80:80 --user root rollogi/php-nginx:8.4
```

Nginx workers run as `nginx`, FPM workers as `nobody`. Use this only when you need ports below 1024; cron does not require it.

## Cron

Scheduled jobs run through [supercronic](https://github.com/aptible/supercronic), which needs no privileges and writes job output to the container log tagged `[cron]`. Configure either a single job with two variables, or mount a crontab, or both:

```bash
# one job
-e CRON_SCHEDULE="*/5 * * * *" -e CRON_COMMAND="php /var/www/html/artisan queue:prune-batches"

# many jobs
-v $(pwd)/crontab:/etc/crontabs/app:ro        # or point CRONTAB_FILE elsewhere
```

Schedules use the standard five fields; a seven-field form with leading seconds and trailing year is also accepted (`*/30 * * * * * *` runs every 30 seconds). The crontab is validated at startup and an invalid one stops the container with the parser's error, so a typo cannot silently disable your scheduler.

In `php-nginx` the scheduler starts alongside Nginx and PHP-FPM whenever jobs are configured. For a dedicated scheduler container use the `php` image with the `cron` command, as shown on its [page](/images/php#scheduler-container).

## File ownership on bind mounts

PHP writes as UID 1000. If your host files are owned by another user, either run with a matching UID or give the mounted directories the right ownership:

```bash
docker run --rm -d -p 8080:8080 -e NGINX_PORT=8080 \
  --user "$(id -u):$(id -g)" \
  -v $(pwd)/public:/var/www/html \
  rollogi/php-nginx:8.4
```

Running as an arbitrary UID works because the runtime state directories (`/run/nginx`, `/run/php`, `/run/cron`, `/etc/nginx/ssl`, `/var/log`, `/var/lib/nginx`) are world-writable with the sticky bit, exactly like `/tmp`, and the entrypoint creates what it needs with best-effort `mkdir`. Nothing under `/etc` or `/usr` is writable by anyone but root. The smoke tests run both images under `--user 4321:4321` to keep this true. With `--read-only`, set the `uid=`/`gid=` options on the tmpfs mounts to your UID, as in the recipe below.

For a team that builds its own images, bake the IDs in once instead. The base image takes `APP_UID` and `APP_GID` build arguments (default 1000), every derived image inherits the user, and the values are exported as `APP_UID` and `APP_GID` environment variables inside the container:

```bash
docker build --build-arg APP_UID=$(id -u) --build-arg APP_GID=$(id -g) -t rollogi/base:latest ./alpine/base
APP_UID=$(id -u) APP_GID=$(id -g) ./alpine/build.sh
```

This is done without any setuid helper: the user is created at build time, so nothing in the running container needs privileges to switch identity.

## Read-only root filesystem

Because configuration never lands in `/etc`, the web images run cleanly with `--read-only`. Any tampering with rendered config or logs is discarded on restart, since tmpfs mounts are recreated.

```bash
docker run --rm -d -p 8080:8080 \
  -e NGINX_PORT=8080 \
  --read-only \
  --tmpfs /run:uid=1000,gid=1000 \
  --tmpfs /var/log:uid=1000,gid=1000 \
  --tmpfs /var/lib/nginx:uid=1000,gid=1000 \
  --tmpfs /tmp \
  --cap-drop ALL --security-opt no-new-privileges \
  -v $(pwd)/public:/var/www/html:ro \
  rollogi/php-nginx:8.4
```

The `uid`/`gid` options matter: Docker mounts tmpfs as root-owned by default. Add `--tmpfs /etc/nginx/ssl:uid=1000,gid=1000` if you use `NGINX_SSL_SELF_SIGNED=true`.

In Compose:

```yaml [compose.yaml]
services:
  app:
    image: rollogi/php-nginx:8.4
    read_only: true
    tmpfs:
      - /run:uid=1000,gid=1000
      - /var/log:uid=1000,gid=1000
      - /var/lib/nginx:uid=1000,gid=1000
      - /tmp
    cap_drop: [ALL]
    security_opt: [no-new-privileges:true]
```

## Why config lives in /run

In non-root mode the user that renders configuration is the same user that executes PHP, so a file-write vulnerability in an application could in principle rewrite php.ini and gain persistence. Keeping `/etc` root-owned and rendering into `/run` means the writable surface is a tmpfs-able directory that resets on restart, and the read-only recipe above removes persistence entirely. It is a mitigation, not a sandbox; treat application-level write bugs as the real problem.

## No setuid binaries

`find / -perm /6000` returns nothing in any image. `busybox-suid` is not installed and the setuid bits from the `shadow` package are stripped at build time, so there is no `su`, `passwd` or `crontab` privilege escalation path for a compromised process.
